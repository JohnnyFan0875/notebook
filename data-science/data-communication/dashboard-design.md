# Dashboard 設計 (Dashboard Design)

單張圖的重點是「看懂」，dashboard 的重點是讓決策者在同一個畫面完成判斷：它同時處理監控、比較與導覽，所以比單張圖更需要一致性與資訊層級。好的 dashboard 讓使用者快速回答明確的問題，例如：這週的關鍵指標有沒有異常？哪個區域或產品線拖累了整體？接下來該追哪個 drill-down？

## 設計前先定義

| 項目 | 問題 | 影響 |
| --- | --- | --- |
| 讀者 (audience) | 主管、分析師、營運、客戶、實驗室？ | 細節程度、術語 |
| 決策 (decision) | 看完要做什麼？ | 哪些 KPI 放最上面 |
| 頻率 (cadence) | 每天看、每週看、即時監控？ | 資料更新頻率、比較基準（昨日、上週、去年同期） |
| 裝置 | 桌機、投影、手機？ | 版面密度、字級 |

先想 dashboard 要支持的決策，再決定每張圖怎麼畫，比先畫圖再拼版面有效。

## 版面層級

```
┌───────────────────────────────────────────┐
│ KPI 卡片 + 警示（與目標 / 上期比較）        │  ← 第一眼：現在正常嗎？
├───────────────────────┬───────────────────┤
│ 趨勢（折線）           │ 分群比較（長條）    │  ← 哪裡出問題？
├───────────────────────┴───────────────────┤
│ 明細表、篩選條件、補充資訊                   │  ← 往下追
└───────────────────────────────────────────┘
```

視線通常從左上往右下移動，最重要的資訊放左上；篩選器放在一致的位置（頂端或左側），不要比內容搶眼。

## 原則

| 原則 | 做法 |
| --- | --- |
| 視覺層級清楚 | 重要資訊大且先看到 |
| KPI 一定有比較基準 | 目標值、上期、去年同期、預測值；單一數字沒有意義 |
| 顏色有語意 | 紅色只用在警示或異常；其他用中性色 |
| 刻度與格式一致 | 同類指標用相同單位、小數位數、軸範圍 |
| 每張圖服務同一個問題脈絡 | 與決策無關的圖拿掉 |
| 互動要設計 | 篩選與連動的範圍明確，不是全部預設打開 |
| 漸進揭露 | 先摘要，需要時才看細節（drill-down、tooltip、明細頁） |

## 常見錯誤

| 錯誤 | 後果 |
| --- | --- |
| 同一頁太多圖、沒有閱讀順序 | 讀者找不到重點 |
| 每張圖都漂亮，但彼此沒有敘事連結 | 像圖表倉庫，不像決策工具 |
| KPI 沒有比較基準 | 不知道數字是好是壞 |
| 顏色太多 | 重點不明，色覺差異的讀者無法分辨 |
| 投影或手機上字太小、圖太密 | 實際使用時看不清 |
| 資料更新時間沒標示 | 讀者不知道看的是不是最新資料 |

## 實驗室與研究情境

研究團隊的 dashboard 多半是監控型：定序 run 的 QC 指標（產出量、Q30 比例、重複率）、樣本處理進度、cohort 收案進度。原則相同：每個指標配上門檻線或歷史範圍，讓異常 run 一眼可見；異常時能 drill-down 到單一 run 或樣本。

| 工具 | 適合 |
| --- | --- |
| Power BI、Tableau | 給非程式使用者、需要權限控管與排程更新，見 [BI 工具](bi-tools/README.md) |
| Shiny、Dash、Streamlit | 研究團隊自建、需要客製分析或與 R / Python 套件整合 |
| Quarto dashboard | 靜態、可重現、定期重新產生 |
| MultiQC | NGS QC 報告的標準工具 |

單張圖的設計與顏色選擇見 [圖表設計原則](../data-manipulation-and-eda/visualization/chart-design-principles.md)。

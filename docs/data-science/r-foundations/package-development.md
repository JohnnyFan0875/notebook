# R Package Development

當 R script 開始跨專案重複使用、需要多人協作，或需要正式文件與測試時，把程式整理成 package 往往比繼續堆腳本更穩定。

Key point: R package 的價值不只是「可以安裝」，而是把函數、依賴、文件、命名空間與測試收進一個可重用的結構。

## Why Use Packages Instead of Scripts

相較於散落的 `.R` 檔案，package 通常更適合：

- 組織函數
- 提升重現性
- 支援協作
- 分享與分發

這不是因為 package 比 script 更「正式」，而是當程式碼開始被反覆引用時，package 能把邊界與責任切得更清楚。

## Minimal Package Structure

一個最小可用的 R package 通常至少有：

- `DESCRIPTION`
- `NAMESPACE`
- `R/`

其中：

- `R/` 放函數程式碼
- `DESCRIPTION` 放套件 metadata 與依賴
- `NAMESPACE` 控制哪些函數會被 export，哪些外部函數會被 import

建立 package 常見起點：

```r
library(usethis)
create_package("unitConverter")
```

## The `R/` Directory

`R/` 目錄是 package 的主要程式碼區。

實務原則：

- package code 應該放在 `.R` 檔
- 不同函數可拆到不同腳本
- 以功能或主題分檔，避免把所有函數堆在同一個巨大檔案

這和一般 script 最大差別在於：這些函數後續會被 namespace、documentation 與 tests 一起管理。

## Choosing a Package Name

package name 應符合基本規則：

- 使用 ASCII 字母、數字與句點
- 避免難搜尋、易衝突或語意不清的名稱

命名除了合法，也要顧及：

- 是否容易辨識用途
- 是否和 CRAN 上既有套件混淆
- 是否能長期維護

## `DESCRIPTION` Is the Metadata Hub

`DESCRIPTION` 不只是描述文字，而是 package 的核心設定檔。

常見欄位包括：

- `Package`
- `Title`
- `Version`
- `Description`
- `License`
- `Depends`
- `Imports`
- `Suggests`
- `Roxygen`
- `RoxygenNote`

課程也特別提到可以用：

- `use_mit_license()`
- `use_gpl3_license()`

來幫助設定授權。

## Dependency Types Matter

R package 依賴不只是一個清單，還有角色區分。

最常見的幾種：

- `Imports`：執行核心功能時真的需要
- `Depends`：會附掛到使用者搜尋路徑，通常應少用
- `Suggests`：測試、vignette 或可選功能才需要

`usethis::use_package()` 很適合管理依賴：

```r
use_package("ggplot2")
use_package("tibble", type = "Suggests")
use_package("glue", type = "Depends")
```

簡單原則：

- 能放 `Imports` 就不要放 `Depends`
- 只在開發或測試需要的東西放 `Suggests`

## `NAMESPACE` Defines Visibility

`NAMESPACE` 控制 package 對外暴露哪些函數。

它通常由 `roxygen2` 自動生成，例如：

```r
# Generated by roxygen2: do not edit by hand
export(distance_converter)
export(temp_converter)
```

Key point: 不是所有寫在 `R/` 裡的函數都該自動成為 public API。export 本身就是設計決策。

## Documentation with `roxygen2`

R package 幫助檔常用 `roxygen2` 直接寫在函數上方。

常見欄位包括：

- title
- description
- usage
- arguments
- returns
- examples
- see also

例如：

```r
#' Convert temperature units
#'
#' Convert a temperature value from one unit to another.
#'
#' @param value A numerical value of the temperature to be converted.
#' @param unit_from A character string of the temperature unit to convert from.
#' @param unit_to A character string of the temperature unit to convert to.
#' @returns A numeric temperature value in the unit specified as `unit_to`.
#' @export
```

這種做法的好處是：

- 文件和函數放在一起
- 修改函數時較不容易忘了同步文件
- `NAMESPACE` 與 help files 可一起生成

## Generating Docs and Namespace

當 `roxygen2` 註解寫好後，可以生成文件與 namespace：

```r
library(roxygen2)
roxygenize()
```

這會更新：

- `man/` 裡的 help files
- `NAMESPACE`

因此 `NAMESPACE` 通常不建議手改，而應把 source of truth 放在 roxygen comments。

## What Good Help Files Should Cover

一個好 help file 至少應讓使用者快速知道：

- 這個函數做什麼
- 需要哪些參數
- 回傳什麼
- 有沒有例子
- 和哪些相關函數一起使用

如果文件只重複函數名，或 `@param` 很模糊，help file 形式上存在但實際上幫助有限。

## Testing with `testthat`

當 package 開始擴張，只靠手動跑函數很難維持穩定。

unit tests 的核心價值是：

- 自動化
- 批次執行
- 驗證預期行為
- 早期抓 bug

它們不只是保護使用者，也保護作者自己在重構時不把既有功能弄壞。

## What to Test

package tests 通常至少涵蓋：

- 正常輸入下的正確輸出
- 邊界條件
- 錯誤輸入是否有合理訊息
- 回傳型別與長度是否穩定

對純函數來說，這和 defensive programming 很搭：先把函數規格想清楚，再把規格寫成測試。

## Installing and Checking the Package

開發過程中常會反覆安裝本地 package：

```r
devtools::install()
```

這一步會檢查基本結構，例如：

- 是否存在 `DESCRIPTION`
- metadata 是否可讀
- package 是否能正常 build / install

雖然課程重點在入門，但實務上通常還會搭配 `devtools::check()` 或 `R CMD check`，在發佈前做更完整驗證。

## A Practical Workflow

可以把入門 package workflow 想成：

1. 用 `create_package()` 建立骨架
2. 把函數整理進 `R/`
3. 用 `use_package()` 管理依賴
4. 在函數上方寫 `roxygen2` 註解
5. `roxygenize()` 產生 `man/` 與 `NAMESPACE`
6. 加上 `testthat` tests
7. 用 `devtools::install()` 與 `check()` 反覆驗證

## Common Mistakes

- 把 package 當成只是「很多 script 放進資料夾」
- 什麼依賴都塞進 `Depends`
- 手動改 `NAMESPACE`，卻忘了 roxygen comments 才是主要來源
- 文件存在，但 `@param` / `@returns` 寫得太模糊
- 完全不測試，只靠手動點幾個函數
- public API 還沒想清楚就全部 `@export`

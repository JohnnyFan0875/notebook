# AWS Security and Cost Management

AWS 的安全與成本管理不是兩條分開的議題。權限太鬆會增加風險，資源治理太鬆則會增加浪費。兩者都在問同一件事：你有沒有把雲端使用方式控制在合理邊界內。

## 先抓兩個核心原則

- 安全上，核心是 `least privilege`
- 成本上，核心是 `visibility + governance`

也就是說，你既要知道誰能做什麼，也要知道哪些資源在花錢、為什麼在花錢。

## Least Privilege

`Principle of Least Privilege` 的意思是，只授予完成工作所需的最小權限。

重點不是讓大家什麼都不能做，而是避免：

- 權限過大
- 權限長期堆積
- 個人帳號被拿去做不該做的事

如果團隊的權限設計是「先開大再說」，那安全與治理通常遲早會出問題。

## Root User 安全

AWS root user 需要特別小心，因為它天然擁有最高權限。

教材裡的實務重點包括：

- 使用強密碼
- 啟用 MFA
- 避免把 root 當成日常操作帳號
- 重要操作可搭配多人審批或共用治理流程

最重要的原則是：root 用於必要的帳號層級管理，不用於一般日常工作。

## IAM: 把存取控制制度化

`IAM` 是 AWS 管理身分與權限的核心工具。

可以把它理解成回答三個問題：

- 誰可以登入或呼叫資源
- 可以做哪些動作
- 可以存取哪些資源

教材強調的幾個方向包括：

- 用群組管理權限，而不是逐人硬配
- 對所有帳號落實 least privilege
- 優先用角色而不是長期保存憑證

## Users, Groups, Roles

這三者最容易混淆，但其實分工很清楚。

### Users

`User` 是具名身分。

適合：

- 真正需要獨立身分的人員
- 需要被審計與追蹤的個別操作主體

### Groups

`Group` 用來把同類型權限分配給一群人。

好處是：

- 權限管理比較一致
- 人員變動時不必逐條重做
- 比較符合部門與職責分工

### Roles

`Role` 通常比長期儲存 credentials 更安全。

適合：

- 應用程式或服務之間的授權
- 臨時取得權限
- 避免把 access key 寫死在程式或主機裡

## MFA 與帳號保護

教材反覆提到一個很基本但很重要的做法：`MFA` 不應只保護 root，也應保護一般 IAM 使用者。

這背後的邏輯很簡單：

- 密碼本身不夠可靠
- 權限帳號一旦被盜用，風險會快速擴大

所以 MFA 不是可選加分，而是基礎防線。

## Security Groups 與邊界控制

IAM 控的是「誰可以做什麼」，`Security Group` 則更偏向「哪些網路流量可以進出資源」。

可以把它們分工理解成：

- IAM 管身分與 API / console 權限
- Security Group 管資源層的網路存取邊界

兩者不能互相取代。

## 成本管理先從可見性開始

雲端成本問題很少是「不知道 AWS 會收費」，而是：

- 不知道哪個團隊在花
- 不知道哪個服務在花
- 不知道哪些資源其實閒置

所以成本管理第一步不是省錢技巧，而是先建立足夠的可見性。

## 三種常見 pricing model 心智模型

教材把價格模式整理成三類：

| 模式 | 核心特徵 | 大致取捨 |
| --- | --- | --- |
| Pay-as-you-go | 用多少付多少 | 彈性高，但預算可預測性較低 |
| Save when you commit | 先承諾使用量或期間 | 彈性低，但節省通常較高 |
| Pay less by using more | 用量增加時單位成本下降 | 介於兩者之間 |

這三類的差異，主要是在彈性、折扣與預算可預測性之間做取捨。

## Pay-as-you-go

適合：

- 需求波動大
- 還在探索 workload 型態
- 不想先做長期承諾

代價是：

- 單價通常不是最省
- 如果沒有治理，浪費也會被原樣計費

## Commitment-Based Pricing

像 Reserved 類型或其他承諾型方案，核心思路是：

- 你願意承諾較穩定的使用模式
- AWS 給你較高折扣

這類方案適合：

- 長期穩定運行的工作負載
- 容量較可預測的核心系統

## 更便宜但有條件的資源

教材也提到像 Spot 這類概念，重點不是背折扣數字，而是理解取捨：

- 價格更低
- 但可用性與中斷風險要一併考慮

因此比較適合：

- 可中斷或可重試的工作
- 非關鍵批次計算

## AWS Budgets

`AWS Budgets` 用來設定預算與通知條件。

它的價值在於：

- 預先設門檻
- 花費接近門檻時提醒
- 幫團隊建立成本警覺

教材也提醒了一個很重要的現實：Budgets 不會自動保證財務控制。它只是告訴你「快超了」，不會替你治理資源本身。

## Billing 與報表視角

教材提到可以追蹤不同團隊或使用者的花費，並建立自訂報表。這件事的本質是成本分攤與責任對應。

沒有這種切分能力時，常見問題是：

- 大家都在用，但沒人對帳單負責
- 共享帳單看起來很大，卻不知道優化點在哪

## AWS Trusted Advisor

`Trusted Advisor` 可以把它理解成 AWS 提供的一種檢查與建議機制。

教材特別提到它能幫助發現：

- 過度配置的伺服器
- 閒置資源
- 一些安全與成本相關檢查點

它不是萬能治理工具，但很適合作為巡檢與發現問題的入口。

## 一個實務上的治理順序

如果團隊剛開始建立 AWS 治理紀律，可以先依這個順序做：

1. 保護 root user，啟用 MFA
2. 用 IAM groups 與 roles 收斂權限
3. 把 least privilege 當成預設原則
4. 建立 Budgets 與成本通知
5. 定期用 Trusted Advisor 檢查浪費與風險

這不會讓治理一次到位，但能先把最常見的風險壓下來。

## 常見誤區

- 把 root 帳號拿來日常操作
- 權限直接配給個人，沒有透過 groups 或 roles 管理
- 以為有 Budgets 就等於已經控制成本
- 成本只看總額，不看服務別、團隊別與閒置資源

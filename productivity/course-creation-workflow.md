# 課程製作流程 (Course Creation Workflow)

一門課不只是寫投影片或練習題，而是一組要同步的產出物（大綱、講稿、練習與解答、提示、錄影），經過設計、開發、審查、上線、維護。沒有明確流程時，常見的結果是延期、學習體驗不一致、目標與練習脫節、上線後的技術債。

## 整體流程

```text
設計                         開發                              上線                  維護
學習目標 → 大綱 → 時程 ──► 講稿 / 練習 / 錄影 → 審查與試走 ──► soft launch → hard launch ──► 回饋與指標 → 修正 → 更新
```

| 階段 | 核心問題 | 主要產出 |
| --- | --- | --- |
| 設計 | 學完後學員要能做到什麼？ | 學習目標、章節大綱、時程 |
| 開發 | 怎麼做出課程、練習、旁白與審查素材？ | 講稿、練習與解答、提示、錄影 |
| 上線 | 品質夠了嗎？ | 試走紀錄、問題清單、分階段發布 |
| 維護 | 上線後怎麼保持正確與有效？ | 回饋處理、指標檢視、內容更新 |

## 1. 設計：從學習目標開始

學習目標是課程設計、內容開發與審查之間的契約，先於投影片製作。

| 好的學習目標要說明 | 例子 |
| --- | --- |
| 學員能理解或**做到**什麼（用可觀察的動詞） | 「能用 `XLOOKUP` 從對照表帶回欄位」而非「了解查找函數」 |
| 預期難度 | 入門 / 進階 |
| 用什麼評量證明學會 | 對應的練習或專案 |

時程要包含的不只是寫作時間：

| 常被低估的項目 | 說明 |
| --- | --- |
| 審查與修改輪次 | 每輪都要排時間 |
| 錄影 / 螢幕錄製準備 | 環境、腳本、重錄 |
| 技術問題 | 練習環境、自動批改出錯 |
| 中斷 | 出差、其他工作 |

> 樂觀的時程一定會失敗，除非把修改與現實干擾算進去。時程的價值在於雙方的責任、過程透明、上線可預期。

利害關係人 (stakeholder) 通常不只一方：講師 / 作者、學員、內部課程團隊、在意採用率與留存的商業端。及早讓各方期待浮上檯面，避免上線時才發現衝突。

## 2. 開發：一組同步的產出物

| 產出物 | 檢查點 |
| --- | --- |
| 章節大綱 | 每章對應哪幾個學習目標 |
| 講稿 | 範例、程式碼、答案前後一致 |
| 練習與解答 | 每題對應一個目標；解答實際執行過 |
| 提示與成功訊息 | 提示指向概念，不直接給答案 |
| 錄影 / 旁白 | 依講稿錄製，術語與畫面一致 |

## 3. 審查與上線前驗證

| 檢查 | 方法 |
| --- | --- |
| 目標 ↔ 練習對齊 | 逐題標出對應目標，找出沒被評量的目標 |
| 指示是否清楚 | 讓沒參與開發的人照著做 |
| 節奏與認知負荷 | 一次只引入一個新概念 |
| 口語是否彆扭 | **唸出來**；默讀看不出問題 |
| 整體學習體驗 | 從頭到尾走一遍完整課程，而不是只審單一片段 |

問題用 issue 追蹤（指示不清、程式碼跑不動、答案錯誤），每個問題要有明確負責人。

## 4. 分階段上線

| 階段 | 目的 |
| --- | --- |
| Soft launch | 先給一小群真實學員，蒐集回饋與品質指標 |
| Hard launch | 品質與表現達標後，再大規模推廣 |

避免在粗糙之處還沒被發現前就大力宣傳。

## 5. 上線後維護

維護是內容生命週期的一部分，不是事後補救。

| 例行工作 | 依據 |
| --- | --- |
| 看學員回饋 | 留言、評分、客服問題 |
| 看完成率與滿意度 | 哪一章流失最多 |
| 修正混淆的指示、提示、程式碼 | 回饋集中的題目 |
| 更新過時內容與套件版本 | 套件改版、API 停用 |

### 修正的責任歸屬

| 作者負責 | 平台 / 工具團隊負責 |
| --- | --- |
| 教學脈絡、指示與提示的文字 | 自動批改基礎設施、測試框架 |
| 範例程式碼 | 呈現與發布系統 |
| 教學上的清晰度 | 練習環境 |

責任清楚可以減少審查來回，避免「應該有人來修」卻沒人修的狀態。
